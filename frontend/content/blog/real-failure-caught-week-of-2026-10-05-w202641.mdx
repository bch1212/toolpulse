The incident below is a reconstruction, not a claim about live customer traffic. It tests a common dependency change: a top-level `results` array being renamed to `items` while the endpoint continues returning HTTP 200.

## The setup

The reconstructed agent uses a tool named `external_search` to retrieve records before a model writes a response. The integration expects this payload:

```json
{
  "results": [
    {
      "id": "doc_184",
      "title": "Retry budgets for agent tools",
      "score": 0.88
    }
  ],
  "request_id": "req_7c2a"
}
```

The caller reads `payload["results"]`, rejects records below a score of `0.65`, and sends the top three titles to the model. ToolPulse wraps the callable and records latency, success, and a value-free response-shape fingerprint.

The tool receives little traffic between 00:00 and 11:00 UTC. A scheduled probe runs every 15 minutes with a known-safe query. It checks that the call finishes within 2 seconds, that `results` is a non-empty array, and that each sampled record contains string `id`, string `title`, and numeric `score`.

## The drift

At 03:07 UTC in the reconstruction, the upstream provider releases a new API version behind the existing endpoint. The response becomes:

```json
{
  "items": [
    {
      "id": "doc_184",
      "title": "Retry budgets for agent tools",
      "score": 0.88
    }
  ],
  "request_id": "req_7c2a",
  "total": 1
}
```

The records did not disappear. Their fields and values did not change. The provider renamed the top-level collection and added a count.

Transport-level monitoring stays green. The endpoint returns HTTP 200 in 164 ms. Authentication works. The response contains valid JSON.

The structural diff is small and breaking:

```diff
- results: array<object>
+ items: array<object>
+ total: integer
```

The added `total` field is harmless. The renamed collection is not.

## What broke

The adapter assumes the old key exists:

```python
def select_results(payload: dict) -> list[dict]:
    return [
        item
        for item in payload["results"]
        if item["score"] >= 0.65
    ][:3]
```

The first production call after the deployment raises `KeyError: 'results'`. The orchestration layer retries twice because the exception is classified as a generic tool failure. All three attempts receive the same structurally incompatible payload.

With 180 ms of network time per attempt and 100 ms backoff between attempts, the agent spends roughly 740 ms proving the same deterministic failure three times. It then returns a generic fallback answer without the retrieved evidence.

A more permissive code path could fail less visibly. If the adapter uses `payload.get("results", [])`, the tool call appears successful and the model receives no records. The observable symptom becomes lower answer quality rather than an exception. HTTP success and tool completion both remain green.

## The fix

The immediate compatibility patch accepts both keys while preserving a metric for the fallback path:

```python
def select_results(payload: dict) -> list[dict]:
    if "results" in payload:
        records = payload["results"]
        source_key = "results"
    elif "items" in payload:
        records = payload["items"]
        source_key = "items"
    else:
        raise ValueError("search response has no result collection")

    if not isinstance(records, list):
        raise TypeError(f"{source_key} must be a list")

    return [
        item for item in records
        if isinstance(item.get("score"), (int, float))
        and item["score"] >= 0.65
    ][:3]
```

The team adds fixtures for both shapes and updates the adapter contract test. It does not automatically promote the new baseline merely because the probe observed it. Baseline approval follows the code change and confirmation that `items` is the provider's intended contract.

In the reconstruction, drift is detected at 03:15, the compatibility patch is ready at 03:31, and the probe returns healthy at 03:36. Time from detection to patch is 16 minutes. The first expected traffic window begins more than seven hours later.

Those timestamps are scenario values, not production measurements.

## What this argues for

First, availability is weaker than compatibility. Fast HTTP 200 responses can be unusable to the caller.

Second, retries should depend on failure class. A timeout may deserve another attempt. A deterministic missing-field error usually does not. Retrying structural failures increases latency and load without improving success.

Third, scheduled checks are most valuable for low-volume, high-impact tools. Production telemetry cannot detect a failure while production is quiet.

Fourth, drift alerts should separate removed, added, and type-changed paths. An added optional field and a removed required collection do not have equal risk.

Finally, reconstructed incidents must remain labeled as reconstructed. No live telemetry supported a real-incident claim this week.
