A reliability fingerprint should change when an agent’s parsing assumptions become unsafe, not whenever a user searches for a different city. Hashing the complete response confuses data variation with contract variation. A shape-only fingerprint removes values, preserves structure and types, and produces a signal that can be alerted on without storing the payload itself.

## Whole-response hashes answer the wrong question

Suppose an agent tool returns:

```json
{
  "results": [
    {"id": "doc_812", "score": 0.91, "title": "Retry budgets"}
  ],
  "request_id": "req_f31a"
}
```

A SHA-256 hash of the serialized response is useful if the question is, “Did I receive these exact bytes before?” It is a poor answer to, “Can the caller still parse this response?”

The next valid request may produce a new document ID, score, title, request ID, ordering, or list length. A whole-response hash changes in every case. In a search workload with 10,000 unique responses per day, you can easily create nearly 10,000 distinct hashes while the API contract remains perfectly stable.

That leads to two bad outcomes. Alert on every new hash and the monitor becomes noise. Learn every new hash as a baseline and the baseline becomes a high-cardinality cache of user data with little reliability value.

A schema regression creates the same hash-level event as an ordinary value change. The signal has no semantic ranking.

## Define shape before you fingerprint it

“Shape” needs a deterministic definition. A practical first version preserves:

- object keys;
- container kinds: object, array, scalar, null;
- scalar types: boolean, integer, number, string;
- the representative shape of array elements;
- optionally, whether a field is observed consistently or only sometimes.

It should discard:

- scalar values;
- object-key ordering;
- array ordering;
- request IDs, timestamps, names, and other volatile content;
- duplicate copies of the same array-element shape.

For the response above, a normalized shape could be:

```json
{
  "request_id": "string",
  "results": [
    {"id": "string", "score": "number", "title": "string"}
  ]
}
```

Serialize that normalized structure with sorted keys, then hash it. The resulting digest remains stable across ordinary searches and changes when the contract changes.

Here is a compact Python implementation:

```python
from __future__ import annotations

import hashlib
import json
from typing import Any


def shape(value: Any) -> Any:
    if value is None:
        return "null"
    if isinstance(value, bool):
        return "boolean"
    if isinstance(value, int):
        return "integer"
    if isinstance(value, float):
        return "number"
    if isinstance(value, str):
        return "string"
    if isinstance(value, dict):
        return {key: shape(value[key]) for key in sorted(value)}
    if isinstance(value, list):
        element_shapes = {
            json.dumps(shape(item), sort_keys=True, separators=(",", ":"))
            for item in value
        }
        return [json.loads(item) for item in sorted(element_shapes)]
    return type(value).__name__


def fingerprint(value: Any) -> str:
    normalized = json.dumps(
        shape(value), sort_keys=True, separators=(",", ":")
    ).encode()
    return hashlib.sha256(normalized).hexdigest()
```

This code is intentionally small. Production implementations need decisions around heterogeneous arrays, optional fields, numbers, and bounded work.

## Arrays are where naive implementations fail

If you fingerprint every array element in order, list length and ranking become part of the contract. A search API returning 20 results instead of 19 appears to drift even though the parser still receives a list of the same object shape.

Using the unique set of element shapes removes length and order. It also preserves useful heterogeneity. If an array previously contained only result objects and suddenly includes an error object, the normalized array gains a second element shape.

There is still a resource limit. A malicious or accidental response could contain thousands of distinct object shapes. Cap the number of elements inspected and the number of unique shapes retained. A reasonable starting policy is the first 100 elements and at most 20 unique shapes. Record truncation as metadata so “stable fingerprint” does not imply “unbounded inspection.”

Empty arrays need special treatment. The value `[]` tells you it is an array but reveals nothing about element shape. Do not replace a known baseline such as `[{"id": "string"}]` with an empty-array baseline after one zero-result response. Keep the last informative element shape, or model emptiness as an observation separate from the structural baseline.

## Type policy should match the consumer

Python makes `bool` a subclass of `int`, which is why the example checks booleans first. JSON also has one number category, while application code often distinguishes integer and floating-point values.

Whether `1` becoming `1.0` is drift depends on the consumer. A TypeScript caller using `number` probably does not care. A Pydantic model with a strict integer field might. Make numeric normalization configurable rather than embedding one universal answer.

Strings present a similar problem. A timestamp, UUID, enum, URL, and free-form paragraph are all strings at the JSON type level. Shape-only fingerprinting deliberately treats them alike. If format constraints matter, layer explicit assertions on top:

```python
assert response["status"] in {"queued", "running", "complete"}
assert response["created_at"].endswith("Z")
```

The fingerprint catches broad structural drift. Contract assertions catch domain semantics. Trying to infer every semantic rule from observed values recreates a brittle schema learner.

## A useful alert reports the diff, not only the digest

A digest is efficient for comparison and indexing, but `8f3c… changed to 9a21…` is not actionable. Store or recompute the normalized shape and produce a structural diff:

```diff
 results[].score: number -> string
 results[].explanation: missing -> string
 request_id: string -> missing
```

Classify changes before paging anyone:

- removed field: usually high risk;
- scalar type change: high risk;
- container change: high risk;
- added field: usually informational;
- new optional array-element shape: investigate, but do not assume outage;
- empty response with retained baseline: availability or data-quality signal, not schema drift.

The classification should follow the caller’s tolerance. An agent that forwards an opaque object can accept changes that would break an agent using direct indexing and arithmetic.

## Shape-only fingerprints reduce data exposure

A normalized shape can often be stored without names, prompts, search terms, document text, or account identifiers. That is not equivalent to zero privacy risk: field names themselves may reveal domain details, and deeply nested structures can be identifying. But it is materially less sensitive than retaining complete tool responses.

The storage difference is also practical. If the average payload is 40 KB and the normalized shape is 900 bytes, retaining one million observations would mean about 40 GB of raw response bodies versus roughly 900 MB of shape documents before compression. Retaining only distinct shapes and counts reduces that further.

Do not turn that estimate into a promise. Actual ratios depend on payload size, uniqueness, compression, and retention policy. Measure with representative traffic.

## Where this advice does not apply

Use a whole-response hash when exact content identity is the requirement: artifact verification, cache validation, deduplication, signed messages, or forensic evidence. Those systems should change their digest when one byte changes.

Shape fingerprints are also insufficient for semantic regressions. A weather tool can keep the same shape while returning Celsius values in a field documented as Fahrenheit. A ranking model can keep every type stable while quality collapses. Pair structural monitoring with domain checks, distribution metrics, and sampled end-to-end evaluations.

Finally, small internal tools with a versioned schema and exhaustive consumer tests may not need runtime shape learning. A generated client plus contract tests can be cheaper and more precise.

The operational rule is narrow: fingerprint the property you intend to monitor. For agent-tool compatibility, that property is usually structure and type—not the complete response. ToolPulse applies that rule at the callable boundary so ordinary data variation stays quiet and structural changes produce a diff an engineer can act on.
